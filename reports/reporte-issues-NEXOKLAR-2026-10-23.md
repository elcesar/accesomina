## Leyenda y metodología

- Severidad de mayor a menor: P0, P1, P2, P3 y sin clasificar. Las etiquetas `sev:critico`, `sev:alto`, `sev:medio` y `sev:bajo` se asimilan a las cuatro categorías. Si no hay etiqueta ni Pn en el título, se deja sin clasificar, sin inferir del lenguaje.
- Estado dentro de cada severidad: **Cerrado → QA aprobado → Listo para probar → En pruebas / QA fallido → En revisión / PR abierto → En desarrollo → Pendiente → Abierto**.
- **Bloqueante** es independiente de la severidad y del estado; se marca solo por etiqueta formal `bloquea-lanzamiento`.
- Fechas de creación proceden de la ficha de cada issue. Fecha último estado corresponde al timestamp `closed_at` para cerrados; en abiertos se declara **No verificable**, pues `updated_at` no equivale a una transición funcional y esta extracción no contiene timeline de estados completo.
- El estado de PR procede de búsquedas GitHub de fusionados, abiertos y cerrados sin fusión; su asociación exige vínculo o referencia `PR #` / `Refs #` / `Closes #` explícitos en bodies, y no implica dependencia de cierre.
- Las relaciones entre issues son **referencias documentadas**, no automáticamente bloqueos; se verificó el estado GitHub de cada ID asociado.
- Los resúmenes se generan de los títulos y del texto estructurado de los issues. No se revisaron exhaustivamente todos los comentarios de QA; no se deben interpretar como retest aprobado.
- **Caso #212:** PR base #177, #189, #201, #203; hallazgos adicionales QA #140 / PR #229 y #283 / PR #313. Las líneas #277 / PR #305 y PR #307 son adicionales, sin dependencia de cierre formal automática para #212.
- Las fechas de extracción y conteos son una **instantánea**, no un dashboard en tiempo real. Para aprobar liberaciones, revalidar despliegues, comentarios y CI en GitHub.
